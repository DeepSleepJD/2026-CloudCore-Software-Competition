# JD v7.4：基于当前任务的执行与验证

以 `feature/jd` 的 `a7b2b00` 为基础，保留三火箭共用炮位、十二段正面墙和工人经济循环，在 `zk_dev` 开发与交付。原 `feature/jd` 分支未修改。

下载 [比赛提交包 CoreGeek.tar.gz](artifacts/CoreGeek.tar.gz) 的文件本体上传，勿上传 GitHub 整个仓库源码压缩包。最新修复和验证见 [v7.4 记录](production/qa/smoke-v7.4-2026-09-18.md)，原有行为见 [v7 交付说明](docs/v7-delivery.md)。

## 启动

解压后平台入口为 `CoreGeek/main3.py`：

```bash
cd CoreGeek
python3 main3.py 8080
# 或
bash run.sh 8080
```

将 8080 替换为平台分配的端口。Python 3.10+，仅标准库，监听 `0.0.0.0`。日志输出到标准输出；GET 健康检查显示 `v7.4-jd`、请求数、最近回合、动作数及异常类型。

提交包仅包含 `main3.py`、`run.sh`、`agent/`、说明与构建信息。仓库中保留的 `zk_agent/`、`config.example.json`、`README-v2.md` 是旧版对照，不是此次部署入口；本版不读取旧配置。

## 本版变化

v7.4 根据当前任务动态绑定参数：补齐跨回合分页证据，允许已知端点分离查询参数；自动读工作区引用规范与同目录接口参考，保留同局成功接口的协议经验，业务参数和答案每题重算。模型生成的修复与本题验收可合并在一次调用，验收脚本 CRLF 在内存适配，原文件保持不变。没有加入比赛城市、答案、凭据、端口或修复命令常量。详细原因与验证见 [完整日志分析](analysis/full-task-log-diagnosis-v7.4.md)。

v7.3 为每道任务记录领取、实际 prompt/executeCmd、模型/沙盒回复、查询和验收参数、提交、判错、超时及撤离原因；调用和回复有编号关联。日志同时打印到标准输出（`TASK_TRACE`）和 `.zk_state/*_trace.jsonl`，按 8MiB 滚动保留 4 个备份，长文本截断明确标记，日志故障不影响出招。修复失败缓存只从内存删除、重启后又加载的缺陷。详见 [失败分析与日志用法](analysis/task-failure-and-tracing-v7.3.md)。

获取新版的运行日志后，可在仓库执行 `python tools/read_task_trace.py teamA.log --output task-trace-decoded.jsonl`，按任务汇总原因并恢复完整调用。日志保留原始任务内容和参数，分享前检查其中的认证和 token；部署包不带本地日志。第一题成功不能证明后续题必成，本版没有把尚未取得的实战调用记录当作已知根因。

v7.2 保留查询失败的 HTTP 状态、认证提示、错误正文和实际返回结构，供模型修正文档中已经过时的参数。仅在分页完整后逐项计算答案：部分字段失败时先提交已算出的字段；若裁判仍允许继续，保留字段错误与已有结果用于修正。未取齐数据时不提交伪统计；没有任何有效字段时继续探索，不提交空对象。10 项新增回归覆盖认证→参数→分页→提交及部分答案纠正，真实模型成功率仍需实战验证。

v7.1 修复“提交形式”标题漏识别；自动定位任务文件，并读取其中明确引用的最多两份 Markdown 说明；每回合命令绑定本题目录，验收目录相对本题路径解析。查询支持本题固定字段，以及文档分开列出服务地址和接口路径的情况。本次没有获得用户最新失败对局日志，不能把这些已复现问题认定为该场全部失败原因。

v7 在 v6 基础上增加查询/工程修复/未知题流程、可配置分页查询与聚合工具、验收 token 核对、答案字段类型检查及重复失败拦截。查询参数和工作目录来自当前题目，工具在裁判沙盒执行。未知或不支持的题目保留通用模型与命令流程；经济、送修及战斗策略沿用已有版本。详见 v7 交付说明。


- 射击首先识别 `targetTeam`，不再为了分数帮助另一队清怪；未知阵营需有接近我方的连续观测或已靠近防线。近距离自保保留例外。
- 接入自进化任务的模型/沙盒异步流程和确认后的解法缓存。任务期间安排工人接炮，夜里任务完成后接班工人继续值守到天亮，避免无人开炮。
- 每天累计新闻，调用比赛模型解析停矿、涨价和宝藏线索；任务外最多三次新闻调用。有防守余款才囤货，缺钱或背包满仍会卖矿。
- 宝藏地点、日期、昼夜、材料齐备且引用新闻原文时才采购和执行；不硬编码这份回放的答案。成功或宝藏已空后停止；材料错误则作废计划，最多两次献祭尝试。
- 根据近期墙体掉血、周围威胁和往日受压情况，预留关键墙维护预算。短时间撑到天亮偏向修墙包，持续承压考虑升级；不盲目给所有墙升级。
- 维修人员先尝试救急用药或近身维修，短途送修会评估人物可承受的伤害；无法承受时撤退。
- 工人保持采矿目标及出售流程；同时购买和在途购买去重，共享金币预算。
- 重复回合请求返回同一决策，显式 null 输入兼容，部署入口沿用 JD。

## 自动化验证

```bash
python -B -m unittest discover -s tests -v
python -B tools/mutation_checks.py
python -B tools/check_replay.py /path/to/replay.json --stride 10
python -B tools/package_submission.py dist/CoreGeek.tar.gz
```

使用风险场景测试、边界组合检查、连续回合小模拟、故意破坏关键行为的变异检查，以及解压后启动真实 HTTP 服务的集成测试。CI 配置为 Linux/Windows × Python 3.10/3.12；Linux 另外运行真实 `bash run.sh` 入口。

任务和新闻测试使用可控的模型回复，不能证明真实 LLM 解题正确率。小模拟不包含完整机器人 AI、对手策略或官方建造区域，回放快照也不计算新策略胜率。部署包不包含原始回放、API 凭据或本地任务缓存。
