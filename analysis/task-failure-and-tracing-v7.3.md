# 任务偶发成功、后续失败：v7.3 分析与日志说明

用户观察：对战 Agentic 麻辣烫时第一题曾成功，但第一题并非每次成功，后续仍有任务失败。现有材料没有这场比赛的 prompt、llmResp、executeCmd、lastCmdResult 原始调用链。以下把代码能证明的问题与需要新日志确认的原因分开，不能将某个风险认定为本场根因。

## 当前实际解题过程

领取任务 → 根据 phaseTask 读取本题任务书及引用文档 → 用 prompt 请求比赛提供的模型 → 下一回合解析 llmResp → 发出 executeCmd 在比赛沙盒执行 → 下一回合读取 lastCmdResult → 提交 submitAnswer，或根据错误继续修正。

修复题有题目提供的验收程序时，使用它产生的 token。查询题由模型识别认证、查询参数、分页、数据路径及字段含义，query 工具取齐数据并计算，再提交。也保留模型编写通用命令和 solve(task) 解法的能力。

**成功一次只证明这一道题的这次调用完成了。** 查询聚合计划目前不会像 skill 一样持久保存；新题通常仍需模型重新理解接口。skill 缓存保存的是返回 solve(task) 的程序，只有通过既有结束条件的候选程序才保存。这不是模型权重训练，也不意味着所有同题型都已掌握。

## 已确认的问题和限制

| 项目 | 代码和测试能证明的事实 | 对“后续为什么失败”的意义 |
|---|---|---|
| 日志不完整 | 旧版主要记录收到的输入；没有完整发出的 prompt、命令和任务结束原因；超过 1MiB 直接重写旧文件 | 无法可靠还原调用顺序，更不能分辨判错、超时和主动撤离；v7.3 已补齐 |
| 缓存失效未持久化 | 已缓存解法运行失败或提交被判错后，旧版仅从内存移除；重新启动会读回磁盘旧解法。任务直接消失的失败路径还可能未移除 | 有失败旧解法重新使用的风险；已用可控输入复现并修复。不能据此断言本场发生了重启或缓存命中 |
| 缓存匹配较弱 | 按题目文本包含 match 子串决定是否复用；AST 检查只验证存在 solve，不能证明参数都来自当前题 | 某题成功的程序仍可能硬编码了城市或认证，换题后失败；日志现在记录缓存标识、匹配词、实际程序及执行结果 |
| 仍依赖模型理解语义 | 正确取齐分页、正确 JSON 类型不能证明筛选、排序、年代含义与题意一致 | 首题偶尔成功符合这一风险；仅凭胜负或成功次数不能确定是哪一字段错 |
| 纠错消耗回合 | 读题、模型推理、执行、再次推理的回复均在后续回合到达；每增加一轮探索就挤占提交时间 | 15 回合任务中反复认证/参数纠错可能来不及；应看实际 remaining 和每次调用，不能只提高次数上限 |
| 生存会中断任务 | 机器人威胁、基地告急、已进入撤离状态会暂停工作或离开任务点 | 夜里与后期的失败可能是生存决策导致；v7.3 记录附近机器人、距离、位置、血量和撤离原因 |

已排除的简单解释：

- 本地接口文档明确说明，自进化任务期间不受任务外每天三次 LLM 限制，且不占任务外额度。不能直接把后续失败归为“第一题用完模型额度”；若平台真实返回 errorCode=5，仍照实记录。
- v7.2 的新任务会重置正文、工作目录、候选答案、已算字段、字段错误、判错答案集合、调用计数。测试验证了连续两题的隔离。目前没有发现“上一题答案必然串入下一题”的证据。
- lastRoundRoleActionResults=true 只表示动作合法，不能单独证明答案正确。新日志不会把合法提交直接标成满分成功。

## 新日志记录哪些证据

每次进程/对局任务管理器创建有 run_id，每次接取有 task_id，每条事件有 event_id。独立编号避免多题、重启及重复请求混在一起。

| 事件 | 内容 |
|---|---|
| task_attempt / task_start | 领取回合、时限、任务原文、是否知道真实起始回合、已有缓存 |
| input | 原始 llmResp、lastCmdResult、errors、角色动作合法性、人物位置；上一条调用的 event_id 和相差回合数 |
| tool_plan / task_contract | 文档路径、实际工作目录、查询/验收参数、答案结构与题型 |
| model_action | 从模型输出解析得到的实际动作及参数 |
| response | 策略最终返回的 prompt、executeCmd 和探险者动作；不是只记录准备执行的意图。它证明程序生成了回复，不单独证明平台已收到或执行 |
| decision | 剩余回合、调用次数、允许工作/提交状态、新增纠错记录、已算字段和字段错误 |
| submission / submission_feedback | 实际提交字符串、提交位置、随后裁判错误及任务是否继续 |
| cache_hit / cache_rejected | 命中的解法标识、匹配词、被移除原因；失败缓存同时更新磁盘 |
| scheduling / survival_action / work_stopped | 机器人威胁、治疗、撤离、基地告急及时间/预算不足 |
| task_end / agent_exception | 任务结束证据，或程序异常类型和内容 |

结束原因使用明确、克制的命名：judge_wrong_answer、judge_timeout、pioneer_missing、base_or_all_actors_missing、task_disappeared_unconfirmed 等。ended_after_accepted_submission 表示已知起始时间、及时提交、动作合法、无错误、下一回合原地任务消失这组证据成立，不宣称知道平台完整评分。如果比赛结束后没有下一次请求，只能记录最后一次提交，汇总会标记结束未观察到。

## 日志在哪里

1. **平台运行日志**：主程序默认把结构化记录打印到标准输出，前缀 `TASK_TRACE `。如果平台提供 teamA.log、容器日志或运行日志下载，可从中取出；普通对局回放不一定含标准输出。
2. **容器本地文件**：默认 `CoreGeek/.zk_state/<队伍摘要>_skills_<run_id>_trace.jsonl`，使用官方 run.sh 启动时位于该目录；从其他目录直接启动 main3.py 时，默认相对于启动工作目录。可以通过 ZK_STATE_DIR 指定位置。
3. **保留规则**：每份文件 8MiB 后滚动，另留 4 个备份（.1 到 .4，.1 最新），不再每 1MiB 清空；不同 run_id 使用不同文件。单个文本值超过 262144 字符才截断，并记录字段路径、原长、保留长度和完整内容摘要。平台命令输出原有 64KB 截断/15 秒超时限制不变。

长事件按短行分片输出到标准输出，避免一条大 prompt 或辅助命令占一整行。恢复工具会报告缺失分片，不把残缺日志伪装成完整证据。本地 JSONL 不分片。文件不可写时仍打印标准输出，记录失败不会阻止提交动作。

仓库中运行：

```bash
python tools/read_task_trace.py teamA.log --output task-trace-decoded.jsonl
```

也可传入多份 JSONL 和轮转文件。工具按任务汇总调用数、答案、裁判错误、停工/撤离原因和结束状态，并输出恢复后的完整事件。工具只读日志，不执行其中的模型代码或命令。日志保留题目、认证参数、token 等原始内容，分享前应检查，部署包不包含已有日志或缓存。

## 后续怎么判断、怎么改

拿到新版产生的日志后，按每个 task_id 查看最后一次有效输入和提交：

- 错误码 2：对比提交内容、题目要求、查询计划及字段错误，优先修正具体字段，不能只反复改提示词。
- 错误码 1：统计用在哪些调用上，识别重复探索或多余模型往返。
- HTTP/业务错误、TIMEOUT、JUDGER_ERROR：定位认证、参数、执行时长或平台故障，不误认成答案逻辑错误。
- survival_action：确认是否为保命主动放弃，再讨论接任务时机或接炮安排。
- cache_hit 后失败：检查旧程序是否正确读取本题参数；失败立即失效，避免重启后继续复用。
- 日志缺失、仅任务消失：明确保留“未知”，不补造原因。

这一版的作用是让失败可定位，并修复已证明的缓存失效问题；尚不能保证任务必然成功。
