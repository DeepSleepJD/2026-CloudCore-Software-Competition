### 直接问题一：单页检查覆盖了跨回合完整性

agent/task_checks.py 的 query_observation 仅接收本次命令输出，用 `总量 != 本页 records 长度` 判定不完整。agent/tasks.py 在每次通用 command 返回后用该结果覆盖 query_issue，没有累计同一查询前面已取得的页。

所以第 32 回合比较的是 15 与 10，第 34 回合比较的是 15 与 5，两次都写入“不完整”。即使历史里已有完整两页，第 35 回合 answer 仍被 query_issue 拦住。

证据：4.log 第 36 行的第一页；5.log 第 11 行的第二页；5.log 第 29 行的模型答案、第 30 行的 answer_error。实际 TaskRunner 输入重放同样没有发出 submitAnswer。

修复不能简单删掉完整性校验。需要按任务、接口和业务参数绑定分页证据，核对 offset 连续、总量一致、唯一 ID 和成功响应。不得把不同城市、不同查询、重复页或缺页混成完整数据；缺乏可靠证据的格式可以引导使用单次取齐的查询工具。

### 直接问题二：同一 API 去掉查询串后被地址检查误拒

文档实际给出的是：

```text
http://localhost:8899/api/v1/heritage/search?city=北京
```

第 36 回合计划把查询参数放到 params，url 使用：

```text
http://localhost:8899/api/v1/heritage/search
```

grounded_url 没有按已观察 URL 的 scheme、host、path 识别同一个端点。它先比较整条字符串，再尝试匹配独立路径；嵌在完整 URL 中的 `/api/...` 前面是端口最后一位数字，不满足它的正则前置边界。因此同一路径被误认为无依据。

使用日志的真实上下文复现返回 False；只用上述两条 URL 的最小用例也返回 False。证据为 5.log 第 44 行 query 计划、第 45 行 query_error。应允许已知同源同路径端点将查询参数单独传入，同时继续拒绝未知主机和路径。

### 补救计划还存在两项质量问题

第 36 回合的 aggregations 漏了 city，并用字符串 era 做 first_by，却未提供工具要求的年代排序 order。用日志的 15 条记录调用当前聚合函数，会得到 `use numeric rank or explicit order, not guessed chronology`。

这是计划参数的确定性问题，但该计划在本场先被 URL 检查拦下，尚未执行，不能称为已发生的沙盒失败。只修 URL 也不足以保证这条补救计划得到完整五字段答案，需要同时处理字段覆盖与字符串年代排序。第 35 回合原答案已经完整，不应被迫进入这条补救路径。

## 为什么此前自动测试没挡住

现有测试覆盖“只收到一页就不能提交”，但没有覆盖“通用 command 分两回合取齐页面后可以提交”。query 工具内部取齐分页的测试不等价于这条通用命令路径。

地址测试覆盖了未知地址拒绝、基础地址加独立路径，漏掉了“文档 URL 自带查询串，工具把查询参数分离”的常见形式。完整修复后还应覆盖重叠页、缺页、总量变化、跨城市隔离，以及这场实际输入第 35 回合可提交的回归。
