# 修复题成功、查询题失败：代码诊断

用户最新反馈：修车任务可完成，其他任务仍失败。现有题面材料中可具体分析的另一类为文化遗产 API 查询；结论不自动扩展至新闻与祭坛任务。当前检查代码为 v7.1，未获得原始查询命令或服务端结果。

## 已复现的缺陷

使用本项目 task_sandbox.run 驱动标准库本地 HTTP 服务，模拟明确的服务端纠错响应；没有访问比赛接口，没有调用真实模型。

| 服务端返回 | 当前工具传给模型的结果 |
| --- | --- |
| HTTP 401，正文说明应使用 Authorization: Bearer 和本题提供的密钥 | 仅 HTTPError: HTTP Error 401: Unauthorized |
| HTTP 400，正文说明缺少 location 参数 | 仅 HTTPError: HTTP Error 400: Bad Request |
| HTTP 200，JSON code=400，message 说明缺少 location | 仅 ValueError: business success condition failed |
| HTTP 200，实际记录数组为 data.items，计划写 data.records | 仅 missing field: data.records，不提供实际结构 |
| 已取得一条记录，count 可计算，但 oldest_era 使用的排序字段为 null | 整个查询失败，已知的统计字段也没有返回 |

直接原因：urllib.request.urlopen 遇到 HTTPError 后跳至外层异常处理，未读取响应正文；业务状态失败时抛出固定文本，丢弃 message；字段解析或某一个聚合项失败后，整个报告 complete=false 并删除 answer。

## 为什么符合两类任务表现不同

工程验收 check 在失败时会保留 stdout/stderr 尾部，使模型有机会根据具体错误修复。查询任务没有同等质量的反馈。已有文化遗产题面明确说 API 文档存在过时字段，因此首次请求失败后的具体提示对纠错很重要。仅在提示词中要求“以真实响应为准”，但实际不把关键响应给模型，是实现上的缺口。

这是查询工具路径的可复现缺陷；若某场使用的是模型自行编写的 command/skill，则须另看该程序如何保留错误输出。现有材料不能证明所有失败任务都经过 query，也不能证明各场实际返回过上述错误。

## 修复优先级

1. 保留有界的 HTTP 状态、错误正文、业务错误信息和实际 JSON 结构，恢复模型的纠错依据。认证值始终取自本题，不硬编码参考仓库中的值。
2. 完整取数后，将各答案字段的计算结果与错误分别保存。单个字段无法确定时保留已确定字段，并明确尚未求得哪些字段；取数失败或分页不完整仍不能伪装为完整统计。
3. 对文档过时→401→修正认证→400→修正参数→分页查询→答案提交建立连续回合测试。此前成功分页测试与错误拦截测试，没有覆盖这条纠错流程。

本次为诊断结论，未修改运行代码或重新打包。它解释了一条与用户反馈相符的失败机制，不是对全部实战失败的唯一归因。
