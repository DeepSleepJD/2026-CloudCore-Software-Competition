# 任务、工人往返、经济与夜间安全分析

日期：2026-09-18。分析对象：zk_dev 的 JD v4（c14e657），以及本地 ../replay.json。仅记录问题和后续方案，本轮不修改运行策略。

用户观察：任务每天失败；一名矿工反复踱步；墙体升级慢；夜间外出人员容易死亡。另记录待设计的“木桶算法”：对修墙、升墙、升炮、升基地比较当前收益，且购买、运输、使用应保持同一目标。

## 证据范围

现有文件是 replay.json：1024 个有效回合，胜方为 defender、teamId 4284。另一队无行动，不能用这局证明强对抗胜率。这不是当前 v4 的失败记录。

回放包含位置、动作、金币、任务描述、最终答案与通过率；没有完整 prompt、llmResp、executeCmd、lastCmdResult。能核对对手何时成功及提交格式，不能还原其沙盒执行程序，也不能诊断当前版本每次任务失败的直接原因。

## 1. 任务需要模型与沙盒配合

当前实际链路：领取任务 → 读取 phaseTask → 发出 prompt → 下一回合解析 llmResp → 发出 executeCmd → 下一回合读取 lastCmdResult → 再请求模型或运行已缓存解法 → submitAnswer。

这使用裁判提供的模型，不依赖本地 Claude。任务期间不受任务外每天三次模型额度限制，见接口文档。当前程序自行设定每题 12 次模型调用、16 次命令预算，达到模型预算后会离开任务点。

### 对手两种题型必须分开理解

| 类别 | 回放中任务入口 | 提交结果形状 | 已知与未知 |
| --- | --- | --- | --- |
| 自进化类1 | task_1_beijing.md、task_2_nanjing.md、task_3_chengdu.md | 城市、记录数、类型列表、世界遗产数量、oldest_era 字段 | 看起来是数据查询/汇总；oldest_era 实际交的是地点名称，不能凭字段名猜格式；具体数据来源须读题目文件 |
| 自进化类2 | task_1_alpha.md、task_2_beta.md、task_3_gamma.md | token 字符串 | 必须按当题文件探索并获取 token；回放不足以判断 token 生成机制 |

对手成功区间分别为 11→14、18→21、112→115、119→123、149→152、156→159，全部 passRate=1.0，每题奖励 80 金币，共 480。完成计数通常下一回合才增长，应以提交回合的通过率、奖励共同判断。

### 当前代码存在的薄弱处

- 两类题共用通用解题提示，没有经过真实沙盒验证的分题型流程。模型必须连“如何读任务文件”也先推断，首次探索成本高。
- 只有模型显式返回 skill，且后续被程序认定成功，才保存解法；直接返回 answer 的成功不会自动沉淀解法。不能把“有缓存代码”理解为已经实现有效自进化。
- 命令结果只保留末尾 20000 字符，上下文只保留最近六条记录，可能遗漏早先的题目约束或接口说明。
- 没有按实际已耗回合、任务超时设置剩余解题计划；接任务的时间判断最多按 12 回合估计，但 12 次模型交互及命令交互可能远超 12 个游戏回合。
- 返回空模型结果、网络错误、沙盒报错等没有细分恢复策略；缺少逐阶段任务诊断日志。
- 缓存确认主要依赖任务消失、动作返回 true 和错误码；接口里的 true 表示动作合法，并非直接代表答案全对，需要检查真实裁判反馈是否足以可靠区分超时、部分分、成功和主动离开。

以上是代码风险，不是已确认的“每天失败”原因。定位具体失败需要本版本失败任务的 phaseTask、prompt、llmResp、executeCmd、lastCmdResult、errors、提交答案和任务起止回合。

## 2. 已复现工人两格往返

最小场景：第 90 回合，一级墙 (28,9) 剩 600 血；工人 (29,9) 满血 220，携带 WallFixer；一个攻击力 40 的机器人位于 (27,9)。保持其他实体状态不变，只按程序输出更新该工人位置，连续决策结果：

```text
90: (29,9) → (28,8)
91: (28,8) → (27,8)
92: (27,8) → (28,8)
93: (28,8) → (27,8)
94—97: 持续在这两格往返，没有使用维修包
```

原因：worker 先执行 urgent_local_supply，再执行 rescue_delivery，再考虑 retreat 和普通 use_supplies。600 血尚未触发低于 400 的近身紧急使用，但触发低于 650 的救援移动。rescue_delivery 排除距离为零的邻墙站位，改选另一处邻墙位置，下一回合再次如此，截断了后面的实际使用逻辑。

这是确定存在的决策循环；静态场景不是完整战斗模拟，不能认定用户看到的工人就是同一情形。在真实战斗中墙继续掉血可能解除循环，也可能先造成损失。

另外，采矿虽保存矿点，却没有保存完整的“采集—出售—采购—送达—使用”工作阶段。修墙、建造、出售等更高优先级每回合都能打断采矿；只锁住矿点不能保证生产连续。

## 3. 墙升级慢不只是钱的问题

规则价格：墙 1→2 花 20，2→3 花 30；炮 1→2 花 100，2→3 花 150。缺少一次 80 金币的任务奖励，足以少买四张一级墙券，但不能因此只增加采矿人数。

当前链路至少有五处约束：

1. 开局三座炮直接花掉全部 75 金币，没有任务收入时只能等卖矿。
2. 两个工人都可能先补齐十二段墙，没有专门保证一人的经济时间。
3. 满血且暂未受压的墙不会主动升级，第一波伤害后才采购，属于规则选择，不一定缺钱。
4. 防守只预留当前一项需求；普通物资使用仍可能优先炮券，采购与配送目标不统一。
5. 墙低于 80% 血量可能触发买维修包，普通使用却要求低于 65%；再叠加已复现的送修循环，出现“有钱、有物资、没有落地”的情况。

应分别记录：现金不足等待、采矿回合、售矿收入、采购等待、送货回合、实际使用回合。收入与交付先恢复，再比较升级收益。

## 4. 夜间安全存在空档

当前不是完全没有避敌：将所有机器人周围四格设为危险区，正常寻路避开；进入危险区时尝试撤退。

但这个规则不足以保命：

- 白天没有机器人时，工人照常前往矿点；没有在首夜刷新前根据返程距离提前避开出生带。
- 夜间只看当前机器人位置，没有用已观测移动方向检查下一步和未来几步的危险。机器人同时移动、角色碰撞会改变结果。
- rescue_delivery 会主动放宽危险区限制，且只估算当前位置、第一步和终点的攻击力，不逐段核验路径，也不考虑撤退余地。
- 已领取任务时，开拓者锁定解题，只有基地紧急情况触发离开，没有自身即将被杀时优先逃生的判断。
- 用药仅在携带药品时有效；现有低血量购药阈值较晚，不能等到危险发生再跑商店。

建议夜间只做有安全去路和退路的短途采矿；天黑前提前收工离开刷新带。安全等待属于有效策略，不能为了“不发呆”让工人冒险。

## 后续优化顺序

1. 补任务阶段日志，用真实任务原文与沙盒结果定位故障，再分别验证两类题的读题、查询、答案校验和解法复用；禁止从回放硬编码答案。
2. 修复送修往返，绑定物资与具体建筑，到位即检查使用；增加多回合无进展检测。
3. 明确经济工人与维修工人的工作阶段，以整趟可兑现收入衡量采矿路线。
4. 增加天黑前撤离、夜间短期危险判断及低血量保命；无法安全赚钱就留在安全区。
5. 最后接入木桶式收益比较。评估的不仅是券价格，还包括能否送到、剩余夜长、维护后能减少多少防守缺口。

已有 77 项自动测试证明的是所覆盖的场景和部署流程，不是完整策略正确性。新增回归必须覆盖真实题型、多回合送修到使用的闭环、天黑前后安全，而不能只断言单回合发出了 move 或 prompt。
