# v3.1：启动结构与空值兼容修复

## 现象和已确认问题

用户反馈上传 v3 后三个角色完全不行动、比赛零分。目前没有取得该次平台启动日志和真实 HTTP 请求，因此还不能确认实际故障发生在哪一层。

已确认两处接入问题：

1. 官方 `Demo/CoreGeek.tar.gz` 有顶层 `CoreGeek/`，入口是 `main3.py`，程序模块位于 `src/agent/`。v3 使用平铺的 `run.sh` 与 `zk_agent/`，没有 `main3.py`。若平台沿用 Demo 启动命令，旧包无法按该路径启动。
2. 官方 Demo 用 `payload.get("robot") or {}` 和 `...get("roles") or ()` 处理空值，旧程序却只处理字段缺失。明确传入 `robot: null` 或 `teamEnemy: null` 会触发 AttributeError；服务捕获异常后返回空动作，能够复现“服务在运行但全员不行动”。

第二项是可复现的程序缺陷，不代表已经证实平台当局传入的字段就是 null。此前使用非空示例请求的测试没有覆盖这种情况。

## 修复

- 提交包恢复 Demo 的顶层目录与同名启动入口，保留 `src/agent/server.py` 的 `serve(port)` 兼容入口。内部策略仍为 zk_agent，不要求和 Demo 的全部源码文件逐一同名。
- 同时支持 `python3 main3.py <port>` 和 `bash run.sh <port>`，入口自行切换到程序目录，不依赖调用方的当前工作目录。
- 对机器人、敌方、角色列表、背包、任务列表、商店列表、可选数值字段的显式 null 进行归一化，不修改传入对象。
- 标准输出记录服务启动地址及每回合动作数；异常保留堆栈。GET 健康检查增加 version、requests、last_round、last_actions、last_error，方便定位接入层故障，不输出模型提示词或题目答案。

## 使用

下载 [`artifacts/CoreGeek.tar.gz`](../artifacts/CoreGeek.tar.gz) 的文件本体上传比赛平台，不要使用 GitHub 的整个仓库源码压缩包。

解压结构：

```text
CoreGeek/
  main3.py
  run.sh
  pyproject.toml
  config.example.json
  BUILD.json
  src/
    agent/
      __init__.py
      server.py
    zk_agent/
      ...
```

启动示例：

```bash
cd CoreGeek
python3 main3.py 8080
```

端口必须替换成平台分配值。如果平台设置工作目录为解压父目录，则启动命令应是 `python3 CoreGeek/main3.py <port>`。本包需要 Python 3.11+，与 Demo 的 pyproject 声明一致。

## 验证

55 项自动化测试通过。新增显式空值回归、空列表/角色默认值回归，以及独立解压压缩包后从不同工作目录启动真实 main3.py 子进程的 HTTP 测试。后三回合请求中 robot、teamEnemy 和 backpack 显式为 null，均有动作，健康检查无决策异常。

压缩包根目录、入口文件、脚本 LF 换行和可执行权限均有检查。当前主机是 Windows，没有可用的 WSL Linux 发行版；入口在本机 Python 子进程验证，尚未在比赛平台或 Linux 容器验证。没有对外声称零分问题已在平台解决。

复现测试与打包：

```bash
python -m unittest discover -s tests -v
python tools/package_submission.py artifacts/CoreGeek.tar.gz
```

如上传后仍不行动，请提供平台启动命令和开头日志。没有 listening 表示启动阶段问题；requests 为 0 表示平台未向服务发送请求；last_error 非空时检查对应异常堆栈。每回合 actions 大于 0 但角色不动，则继续核对平台动作执行错误反馈。
